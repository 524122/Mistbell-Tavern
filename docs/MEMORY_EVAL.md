## 三、夹具

- 12 个中文合成会话，各 300 楼，每条消息平均 20–23 字。
- 360 条可核对事实：120 条后续被更新，189 条带换说法的重述。
- 144 个探针，分三类：前段 60 个问「不带更新的事实的原话」（26–126 楼）；中段 36 个问「稍后会被更新的事实在更新前的原话」（150–200 楼）；后段 48 个问「更新后的新版本」（226–300 楼）。
- 探针与事实原话**没有任何连续两个汉字相同**（人名与一组虚词除外），也不含取值词。这是「换说法」的硬模式：词法那一路在目标事实上天然是零命中，全靠语义或重要度。
- 上下文预算 2048 token。实测历史窗口 25–74 楼（中位数 52 楼，约 26 轮），记忆块越大留给历史的越少。1024 是窗口只剩约 7 轮的极端情形，只作敏感性对照。
- 探针「有效」的判定：目标事实的原话楼、重述楼、更新楼（探针之前已发生的）都不在历史窗口里。默认预算下 144 个探针里 91 个有效（前 11、中 32、后 48），其余不计入命中率分母。

夹具的写法与校验规则见 `.e2e/eval/memory/README.md` 与 `SPINE_SCHEMA.md`。

## 四、指标

| 指标 | 定义 |
|---|---|
| 抽取召回率 | 事实版本（原版本 + 更新版本）中，回放结束后记忆库里至少有一条对应记忆的比例 |
| 注入命中率 | 有效探针中，目标事实的目标版本在该探针楼的注入记忆里出现过的比例 |
| 过期注入率 · 行级 | 注入的记忆行里，匹配到「在该楼已被更新的旧版本」的行数 ÷ 匹配到任何事实的行数 |
| 过期注入率 · 探针级 | 后段探针中，旧版本仍被注入的探针数 ÷ 后段有效探针数 |
| 重述负例 · 恰好一条 | 带重述且不带更新的事实里，回放结束后对应记忆恰好一条的比例 |
| 噪声率 | 注入的记忆行里，不匹配任何埋点事实的行数 ÷ 注入行数 |
| 成本 | 每个有效探针楼注入记忆的 token 估算；抽取调用次数 |

一行记忆归属哪条事实：归一化后包含该事实的 `object`，或与该版本陈述文本（原版本 = 原话 + 重述；更新版本 = 更新句）的字符二元组 Dice ≥ 0.5，取最高者。

## 六、从数字里读到的

1. **结构化记忆块与当前问题基本无关。** `selectRelevantMemories` 每轮最多选 10 条：重要度 ≥ 8 的前 5 条、档案类 ≥ 6 的 3 条、与当前消息关键词匹配的 3 条。探针与原话零词面重合，关键词那一路拿不到分，于是每轮注入的几乎是同一批高重要度记忆。命中率实际上等于「目标事实是否恰好排在那一批里」。预算 1024 一列的总命中率更高，不是记忆变好了：窗口更小之后前段探针大量变成有效，而前段指向的事实多排在前面。分三类看，前段 7/11 对 38/51、中段 12/32 对 14/36，基本没变。
2. **更新后的新状态进不去，旧状态一直在。** 更新版本的探针命中只有 6/48（JVM）与 9/48（设备侧）；后段 48 个探针全部注入了已被更新的旧版本。按代码读到的机制（未单独测量）：选择器同重要度下按访问次数排序，而每注入一次访问次数加一，于是先进去的旧版本越排越前。
3. **重述不被去重。** ORACLE 口径下 148 条带重述的事实，没有一条在回放结束后只有一条对应记忆。真实模型会把原话和重述都改写成第三人称，两句会更接近，去重有机会生效，待 RECORDED 确认。
4. **词法回退的召回块带来噪声。** JVM 上注入行里 13%–20% 匹配不到任何埋点事实，基本是词法召回带进来的闲聊原句。
5. **向量召回没有把命中率救起来，噪声却高得多。** 修复前设备侧命中率只比 JVM 高不到 3 个点，噪声率从 14.2% 升到 30.5%。向量路把语义相近但与事实无关的闲聊捞了进来。自带模型的区分度本来就窄：换说法的同义对余弦均值 0.70，无关对 0.57。
6. **召回块的名额在浪费。** 失败样例里召回块的第一条永远是探针自己，还会捞回三楼之前的闲聊。原因在代码里：词法那一路自带「近期窗口排除」，向量那一路既不排除当前消息，也不排除已经在历史窗口里的消息。诊断量过：召回块前五里平均 2.3 个被「最近 50 楼内的消息」占掉（见第十节）。第十一节把它修掉之后，设备侧命中率 30.1% → 33.3%，噪声 30.5% → 27.9%。
7. **重要度低于 7 的记忆没有向量副本。** 向量同步只给重要度 ≥ 7 的记忆留摘要副本，其余记忆在语义检索里不可达，只能靠原话所在的那条消息向量间接找到。诊断量过：只有 44% 的探针，其目标事实有摘要向量；有的那一半 recall@5 是 51.6%，比消息向量那一路好得多。
8. **查询端不加 BGE 的指令前缀是对的。** `LocalEmbeddingService` 对查询和正文用同一种方式编码。我原本怀疑这是个用法错误，诊断量下来相反：加上前缀之后目标原话的 recall@5 从 14.6% 掉到 8.3%。

## 七、这套评测的已知局限

- **两种配置各只测到一路。** JVM 只有词法路。设备侧的词法路固定读真实容器库（`LexicalMemoryService` 的库取自 `AppContainer`），评测会话不在其中，所以恒为空。真机是两路一起参与融合，命中率与噪声会与本页有出入。
- **夹具的探针句式单一。** 每个会话 12 个探针都是「…还记得…吗」，彼此最相似，向量召回会先捞回以前的探针。真实对话里不会有这么多孪生问题。诊断量过：去掉其他探针后 recall@5 只从 14.6% 升到 16.7%，影响约 2 个点。
- **ORACLE 的 `rawText` 是原话逐字。** 记忆正文与历史原文完全一致，对词法召回偏乐观；重要度是定档合成的，不是模型判断的。
- **时序是理想情况。** 探针楼装配时，之前所有批次的抽取与向量同步都已完成；探针自己的消息向量在装配前已经落库，生产里是异步的。第十一节的修复把当前消息与最近 40 条排除在召回之外，这一点不再影响召回块。
- **设备侧只读接触了真实库的一个键。** 生产 `MemoryExtractionService` 的抽取模板设置取自真实容器库，评测无法注入。测试里有哨兵：模板不是默认值就判失败。
- **注入清单取自装配器的溯源字段。** 评测交叉校验了「清单里的条目确实出现在提示词文本里」，但查不出「装配器把不该注入的内容写进了清单」这类两侧一致的错。

## 八、评测自身改过的地方

- **历史窗口的判定。** 最初用「正文是否出现在历史段里」判断，夹具的闲聊轮会循环复用，同一句话前后都出现，窗口最早楼层被算得很乱。历史段其实是会话消息的连续后缀，改成按历史段条数算，并加了一条口径断言。有效探针的判定不受影响（它只看目标事实自己的原话楼）。
- **记忆行与事实的匹配。** 最初原版本只用原话一个文本去比，由重述抽出的记忆条目归不回事实：被算成噪声，「重述后恰好一条」把去重失败记成了成功（当时是 36.5%）。改成原版本的匹配文本 = 原话 + 重述之后，噪声率从 23.2% 降到 14.2%，恰好一条从 36.5% 降到 0%。
- **设备侧补上了向量同步。** 评测驱动是直接插消息行的，绕过了生产里给消息写向量的环节。设备侧用生产同一套触发器、outbox 与排空入口把这一环补齐，并断言写进去的条数。
- **JVM 数字现在可复现。** 同一份输入连续跑，过期注入的行数在 335 与 336 之间跳过。查下来是时间戳并列：记忆的创建时间由生产代码取 `Instant.now()`，同一批里先后保存的两条只隔几微秒，而这台机器上 `Instant.now()` 约十几微秒才变一次，两条偶尔拿到完全相同的时间戳，排在入选边界上的那一条就翻转。替身数据库的排序加了并列定序（按 id 降序，方向与「新的在前」一致）之后，连跑四次报告正文逐字节一致。

## 十一、闸门触发后做的那一轮管线修复

**改了什么。** 向量召回的候选先剔除「当前消息 + 当前会话最近 40 条消息」，再进入融合。40 与词法路同源：同一个常量、同一条 DAO 查询。此前只有词法路有这个排除。召回是在历史窗口选定之前算的，所以两路都用「最近 N 条」来近似历史窗口。

**没改什么。** 向量候选的过取倍数保持 3。设备侧在 3、4、5 三档下命中率完全相同，噪声只差 1–2 行；倍数 3 剔除之后每个探针仍保留约 11 条候选，是 topK 的两倍。没有改提示词，没有改阈值。

**效果（设备侧，ORACLE）。**

| 指标 | 预算 2048：修复前 → 后 | 预算 1024：修复前 → 后 |
|---|---|---|
| 注入命中率 | 30.1% → 33.3% | 45.2% → 47.4% |
| 其中更新版本的探针 | 14.6% → 18.8% | 14.6% → 18.8% |
| 噪声率 | 30.5% → 27.9% | 31.6% → 27.5% |
| 过期注入率 · 行级 | 37.1% → 36.5% | 29.0% → 28.8% |
| 过期注入率 · 探针级 | 48/48 → 48/48 | 48/48 → 48/48 |
