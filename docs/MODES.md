# 玩法模式设计（设计稿 · 决策记录）

> 状态：**设计定稿，分期实施**。本文记录五种玩法模式的统一架构、当前开发范围决策，
> 以及"骨架预留"的具体含义。模式①为现状；模式③②为近期范围；模式④⑤仅留骨架，后续开发。
> 背景：多轮设计讨论（2026-08）+ 对 SillyTavern 生态的参照调研。

---

## 核心抽象

一个会话 = 一份模式配置。玩法不是代码分支，而是四个参数的取值：

```
Session {
  speakers:     [Speaker]    // 模型扮演的一方（1..n）
  personas:     [Persona]    // 被描绘的人设（属于模型、用户或叙事者）
  memoryScopes: [ScopeKey]   // 记忆归属域，格式 "<kind>:<id>"
  assembly:     组装策略      // 各层记忆的优先级与预算分配
}
```

设计原则：**出现下一种玩法时是填表，不是改管道**。抽取、查重、召回、
token 预算、世界书触发等底层管道对所有模式共用。

## 五种模式

| # | 模式 | speakers | personas | memoryScopes | 状态 |
|---|---|---|---|---|---|
| ① | 经典聊天 | [角色卡] | [角色卡] | `user:global` + `char:<卡>` | ✅ 现状（隐式配置） |
| ② | 扮演反转 | [世界叙事者] | [角色卡=用户] | `char:<卡>` + `world:<设定>` | 🚧 近期 |
| ③ | 群聊 | [NPC×n] | [NPC×n + 用户] | 按 NPC 分账 + `user:global` | 🚧 近期 |
| ④ | 导演模式 | [叙事者] | [剧情人物们] | `canon:<story>`（时间线优先） | 🦴 仅骨架 |
| ⑤ | 卡对卡剧场 | [卡A, 卡B] | [卡A, 卡B] | 双角色 + `canon:<story>` | 🦴 仅骨架 |

### 模式② 的准确形态（重要，防过度设计）

模式②的本质是**角色扮演反转 + 叙事姿态**，不是游戏模式：

- **结构层（模式本体）**：角色卡写入用户 persona 槽位；AI 为世界叙事者；
  第二人称叙述；记忆 subject 重定向为"你的角色 + 世界设定"。
  叙事者提示词必须包含**代理权保护条款**：不得替用户角色行动/发言/下判断。
- **内容层（自由）**："异世界探索"等背景来自世界书/设定卡/开场白，与模式无关。
- **规则层（可选，默认关闭）**：骰子/状态栏/物品栏/检查点属于少数派"游戏感"需求，
  以"规则包"形式提供，不进默认体验。无规则包时长局事实漂移由记忆管道兜底即可。

ST 生态参照：GM 玩法主流即此形态（Sukino Game Master Mode 等预设）；
带骰子的（ZDOSt/Game-Master）是少数。不要拿最重的形态代表需求。

### 模式③ 群聊要点

- 现有 `participantCharacters`（≤4 人）是现成地基，缺：说话方轮转策略、
  历史消息说话者标注、按 NPC 分账的记忆（含 **witness 可见性**：
  NPC 只召回自己在场时产生/获知的记忆——知识不对称是群聊沉浸感的灵魂）。

### 模式④⑤ 形态速记（供未来开发）

- ④：用户是编剧，下场景指令；模型只输出叙事。记忆=剧情正典（append-only
  事件时间线 + 章节摘要），召回按时间线/场景而非相似度。闪回=按节点取上下文。
- ⑤：模型自扮演双方、自动轮转；用户输入为舞台指令（continue/情绪引导/换景），
  不进对话流。记忆按说话方分账 + 正典。

## 视图层：主题包（决策）

**原则：卡不带 UI。** 角色卡是纯内容制品，保持 chara_card 规范可移植；
呈现归独立的**主题包**（插件制品），需要对应状态约定时配**规则包**。

### 三制品栈

```
角色卡 = 纯内容（人设+提示词+世界书），不带 UI
规则包 = 状态约定（可选）：状态 schema + 结构化输出协议（如 "battle-v1"）
主题包 = 呈现：theme tokens（色/字体/气泡/背景）+ 可选 ui.html 沙箱面板
```

耦合点是**状态约定**而非相互引用：规则包声明产出 `battle-v1` 状态，
主题包声明消费 `battle-v1`——同约定可互换，组合自由替代点对点绑定。
示例：宝可梦规则包（HP/技能/回合的状态增量输出）+ 宝可梦战斗主题包
（HP 条/技能格/战斗日志面板）= 可操控的战斗 UI；两者皆可独立更换。

### 主题包结构与分级

```
theme-pack.zip
  manifest.json  { id/name/version/author,
                   capabilities: cosmetic | interactive,
                   consumes: ["battle-v1"], appliesTo: 会话|角色|全局 }
  theme.json     皮肤 tokens                        ← 皮肤级：纯数据
  ui.html        沙箱面板（可选）                    ← 交互级：WebView 沙箱
  assets/        背景图等
```

- **皮肤级**：纯 tokens，无代码，安装即用（首版只做这级）。
- **交互级**：ui.html 在 WebView 沙箱运行（禁文件访问/跨源，CSP 锁死），
  桥协议仅四方法：`onState`(状态快照)/`onChat`(消息流)/`sendMessage`/`setDraft`；
  安装时明示"包含交互界面"。页面接触不到 API key、数据库、原生接口。
- **安全模型**：卡片永远是数据（天然安全）；可执行内容只经主题包安装这一
  显式动作进入。不做消息流内嵌 WebView——沙箱面板只在面板区，消息流原生渲染。

### 应用链与推荐

**会话指定（已实现，聊天设置中选取，v11 迁移 sessions.theme_id）** → 卡片推荐（`recommendedTheme: <id>`，仅提示，缺省回落，待卡导入解析支持）→ 全局 → 默认 UI。
未声明/未安装主题包的卡零成本回落默认聊天 UI。

### 与模式工作的依赖

皮肤级主题包独立可先行；交互级依赖状态层（模式②规则包 / 状态约定）——
桥推送的 `onState` 就是权威状态，跳过状态层会做出与叙事脱节的贴图 UI。

## "骨架预留"的定义（决策）

**预留（现在就做，成本极低）：**

1. `SessionMode`/模式配置在 schema 上可表达全部五档（含多 speaker 列表结构），
   未来加模式**不需要数据库迁移**；
2. `ScopeKey` 采用 `<kind>:<id>` 前缀格式（`user:` / `char:` / `world:` / `canon:`），
   ④⑤ 的 `canon:` 域未来只是新增前缀与过滤器；
3. 本文档本身：④⑤ 的形态、示例与要点已记录，未来开发有据可依。

**明确不做（吸取本仓库教训，见 ROADMAP M2-1 死代码清创）：**

- 不建空的 UI 入口/设置项（反例：设置页六个空 onClick）；
- 不建无调用方的半成品服务（反例：SyncManager 空壳）；
- ④⑤ 在界面上**完全不露出**，直到真正开发。

## 实施顺序

```
① 现状（零成本）
T1 皮肤级主题包：主题 tokens + 应用链（会话/推荐/全局/默认回落）+ 导入导出
③ 群聊：speaker 标注 + 轮转 + witness 记忆分账（复用 participantCharacters）
② 扮演反转：反转开关 + 叙事者模板（含代理权保护）+ 记忆 scope 重定向
              （MVP 仅此三动作）
R  规则包 + 状态约定（battle-v1 等）：状态 schema + 结构化输出协议
T2 交互级主题包：ui.html 沙箱 + 桥协议（onState/onChat/sendMessage/setDraft）
④⑤ 后续开发（骨架已备）
```

T1 独立于模式工作、可与 ③② 并行；T2 必须在 R 之后（桥推送的即权威状态）。

与 ROADMAP 的关系：模式工作排在 M1/M2（正确性与清创）之后；
记忆 scope 化与 M2-3（AppContainer/DI）、AU 会话隔离改造是同一批底层变更，
应一并设计实施。
